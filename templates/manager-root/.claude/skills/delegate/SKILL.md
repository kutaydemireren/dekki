# /delegate [project] <task>

You are the manager. Do not implement or verify yourself. See `CLAUDE.md` in this folder for the project map, preferences, guardrails, docs rules, report contract, project setup and the "Work across projects" playbook.

1. **Resolve the project(s)** from the map in `CLAUDE.md` (match folder names loosely). If the map is empty, `ls` the folder to learn the projects. If the user named no project, work out which are involved (read-only scoping) instead of asking. If the task touches more than one project, follow "Work across projects" in `CLAUDE.md`: state the plan, fix the shared contract first, one worker per project with the same `--name` feature slug, and cross-check the results before reporting. If it is ambiguous or a folder is not a repo, ask one question or work in place.
2. **First-time setup.** If `.claude/harness.json` has no entry for the project under `projects` (`delegate.sh` warns about it too), do the "Project setup" steps in `CLAUDE.md` before the first delegation: say "first-time setup for <project>", read the project, propose the build, lint, scoped test and full test commands, the sensitive paths, the UI paths and the visual proof, ask the user once with `AskUserQuestion`, then run `.claude/scripts/project-setup.sh`. Skip this when the project already has settings.
3. **Read the docs, then write a self-contained brief.** First read `<docs>/<project>/START-HERE.md` and the newest `LOG.md` entry (hard rule in `CLAUDE.md`). The brief has the goal, relevant files/tickets, constraints (worktree + branch for edits, what not to touch), the definition of done and the line `docs read: yes`. Don't list tests, don't write an expected tier and don't ask for the full suite: the worker runs only the floor until you classify its diff ("Verification tiers" in `CLAUDE.md`). Write `Verification tier: N` only when you deliberately preset a tier. Don't paste secrets. The script appends the guardrails, the project's docs path and its check commands for you.
4. **Launch**: `.claude/scripts/delegate.sh <project> "<brief>" --name <short-slug>`. Note the printed id. If it fails with a trust error it prints the exact command: ask the user once with `AskUserQuestion` ("Trust first" in `CLAUDE.md`), then run the same call again. Workers run at medium effort by default; add `--effort high` only when asked or clearly needed. `delegate.sh --check [<project>]` validates the setup and shows what a brief gets, without starting anything.
5. **Tell the user in one line** which worker you started, where, and what it is doing. Then continue other work.
6. **Monitor**: status via `claude agents --json --cwd <project>`; read results from the worker transcript (`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<project path>/<id>-*.jsonl`, last assistant text), since `claude logs` is raw terminal output. Wait with `.claude/scripts/wait-worker.sh <id>` run in the background (exits when the worker stops `working` or its `status` is `idle`, which wakes you; its last line shows the worker's last message, and `state` alone can lag, so check that message), or `notify_when_idle` on your SendMessage, not tight polling. Never end your turn with workers running and no wait pending: "I'll report back" wakes nothing, and you would stay "working" forever.
7. **Follow-ups**: `SendMessage` to the live worker by name (with `notify_when_idle: true`) to answer a `needs input:` or request fixes. Never `--resume` a live worker: it forks a new session. For a worker that has exited: `.claude/scripts/delegate.sh --resume <id> <project> "<message>"`. With no flag that continues the same session with its saved options; `--effort <level>` starts a copy under a new id (the script says so), so use it only when the effort must change. Answer from known context when you can; relay to the user only decisions that are theirs.
8. **Report back**: summarise the worker's `result:` / `needs input:` / `failed:` in plain language with branch, path or PR and the evidence. Surface `needs input:` immediately. Before reporting done (and before any commit), run `.claude/scripts/classify-change.sh <worker worktree> [--project <folder>]` on the diff, tell the worker any checks the tier adds, and wait for them. When they pass, have the worker (or yourself, if it has exited) amend the dated `LOG.md` entry with the checks that actually ran. Check that the report names the docs the worker touched. Don't call it done without evidence that matches the tier.
9. When finished, `claude stop <id>` any idle worker (its conversation is kept).
